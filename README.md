# Archaeo Doc Pipeline

## Controlled Delegation under Unreliable Evidence

Предметная экспериментальная среда для проекта **Designing and Evaluating a Human–AI Delegation Workbench for Reliable Agentic Task Execution**.

Исследуем границу автономии AI-агента при работе с неполными, искажёнными и неоднозначными свидетельствами: когда продолжать самостоятельно, когда проверять оригинал, когда обращаться к человеку и когда оставлять вывод неизвестным.

Корпус археологических отчётов ИА РАН служит реалистичной средой, в которой ошибки OCR, неверные извлечения и ненадёжные метаданные могут превращаться в неподтверждённые утверждения. Цель — не исправить весь архив, а измерить, как управлять этим риском при ограниченном бюджете контроля.

> Статус на 14 октября 2026 года: обработка корпуса завершена. Агентный слой, политики контроля и эксперименты пока планируются. Работоспособность предложенного подхода, его научная новизна и переносимость не доказаны.

## Исследовательский вопрос

> How do delegation and runtime control policies affect an agent’s ability to complete evidence-based tasks under unreliable data, balancing unsupported claims, useful completion, verification cost, and human intervention?

Практическая цель — полезное выполнение без постоянного ручного надзора. Исследовательская цель — установить компромисс между автономией, качеством результата и стоимостью контроля. Это ограниченное исследование механизмов делегирования, а не заявление о решении общей проблемы AI alignment.

## Задача агента

Агент получает поручение составить структурированное описание одного археологического комплекса: обозначение, местоположение, размеры, явно описанные находки, авторская датировка. Набор полей уточняется на пилоте.

Доступны OCR-тексты, извлечения и сканы. Каждое заполненное поле должно иметь ссылку на отчёт и страницу, конкретное свидетельство и статус проверки. Авторскую интерпретацию необходимо отличать от непосредственно описанного наблюдения. Если оснований нет, поле остаётся неизвестным с указанием причины.

| Проблема данных | Решение агента |
|---|---|
| Возможная ошибка OCR | Принять текст или проверить изображение |
| Подозрительная сущность | Использовать извлечение или сверить контекст |
| Отсутствие извлечений | Проверить источник, а не объявить сведения отсутствующими |
| Неоднозначное соответствие объекта и описания | Запросить уточнение или воздержаться |
| Ненадёжная метка страницы | Не исключать свидетельство только по автоматическому `page_type` |

Наличие пропущенных страниц и противоречий между текстом и планами ещё требуется установить по конкретным случаям. Контролируемые изменения данных отмечаются отдельно от естественных дефектов.

## Один сквозной прототип

```text
Поручение и ограничения
        ↓
Агент → чтение OCR / просмотр скана / запрос человека
        ↓
Runtime-контроль разрешений, checkpoints и бюджета
        ↓
Описание со свидетельствами или обоснованными пропусками
        ↓
Проверка результата и журнал траектории
```

Workbench управляет поручением, утверждением плана, вмешательствами и остановкой. Этот проект предоставляет предметные инструменты, задачи и оценивание. Не создаём второй независимый интерфейс управления.

Исходники доступны только для чтения; запреты обеспечиваются средой, а не только промптом. Логи фиксируют доступные свидетельства, вызовы инструментов, проверки, запросы человека, ответы и итоговый результат. Обращение к человеку может закончиться ответом «не знаю» и не разрешает выдумывать отсутствующие данные.

## Дорожная карта и критерии перехода

### 1. Проверить постановку на 10 случаях

Начать с одного полностью разобранного случая, затем расширить до 10: поручение, доступные материалы, дефект, проверенные значения и допустимые причины воздержания. Полная расшифровка корпуса не нужна; выбранные утверждения и основания проверяются вручную.

Пилот должен показать, что задачи имеют проверяемый результат, а дефекты действительно создают содержательные решения о проверке и делегировании. Десять случаев — разведочный этап, не достаточное основание для широких выводов.

### 2. Реализовать минимальный сквозной запуск

Подключить одну модель к инструментам корпуса, контролю действий, журналированию и проверке полей. Результат этапа — воспроизводимый запуск от поручения до оценённого ответа, а не набор несвязанных скриптов.

### 3. Сравнить режимы контроля

При одинаковой модели, задачах и инструментах сравнить:

1. Свободное выполнение без обязательных checkpoints.
2. Структурированный бриф с фиксированными checkpoints.
3. Тот же бриф с проверками по заранее заданным признакам ненадёжности.

Такое сравнение сначала оценивает целые конфигурации. Чтобы выделить эффект checkpoints или структуры брифа, провести отдельные ablation-эксперименты, меняя один механизм за раз.

### 4. Разработать собственную политику контроля

По ошибкам базовых режимов выбрать один механизм: решение между проверкой источника, запросом человека, продолжением и воздержанием при ограниченном бюджете. Сравнить его с простыми правилами на случаях, не использованных при разработке.

Обучаемый контролёр вводится только при наличии достаточных траекторий и проверяемой гипотезы преимущества. Добавление ML само по себе не является результатом; нужен измеримый выигрыш в компромиссе качества, полноты и затрат.

### 5. Проверить переносимость

Если эффект подтверждён, использовать второй тип документов вне археологии. Зафиксировать неизменяемую часть политики и отдельно учитывать необходимую адаптацию. Отрицательный результат также публикуется: он показывает границы подхода. Выбор второго корпуса и права использования ещё не определены.

## Метрики и протокол

| Метрика | Назначение |
|---|---|
| Корректность заполненных полей | Соответствие проверенному свидетельству |
| Полезная полнота | Доля правильно заполненных полей среди тех, на которые доступен ответ |
| Неподтверждённые утверждения | Отсутствие достаточного основания в доступных материалах |
| Качество воздержания | Корректные отказы и отказы при достаточных данных |
| Соблюдение политики | Нарушения запретов, пропущенные обязательные проверки |
| Стоимость контроля | Число и длительность вмешательств, время, стоимость модели, tool calls |

Оценивать показатели совместно: постоянное воздержание или передача всей работы человеку не считаются успехом. Необходимость проверки определяется проверочной разметкой, а не заявленной моделью уверенностью. Критерии проверки и веса затрат фиксируются до итогового эксперимента.

Условия воспроизводимости:

- одинаковое начальное состояние, инструменты и бюджеты;
- раздельные случаи для разработки и итоговой проверки, по возможности на уровне отчётов;
- повторные запуски, фиксированные версии и настройки, отчёт о разбросе;
- раздельная отчётность по естественным и искусственно введённым дефектам;
- одинаковый протокол помощи человека; фиксированные ответы в пилоте не заменяют пользовательское исследование;
- различение ошибок данных, инструментов, модели и политики контроля.

Субъективную управляемость, понятность и доверие проверяют отдельно с участниками Workbench; автоматические логи их не измеряют.

Воспроизводимые случаи и проверки, интеграция с Workbench, журнал траекторий, сравнительный эксперимент и собственная политика контроля с явно указанными ограничениями. Реализованные результаты отделяются от гипотез. Переносимость проверяется экспериментально, а не предполагается.

## Корпус

### Происхождение

Отчёты хранятся в Научно-отраслевом архиве Института археологии РАН. Архив собирает научные отчёты об археологических исследованиях на территории страны с 1945 года ([Научный архив ИА РАН](https://archaeolog.ru/scientific-departments/archive/)); сейчас поступает около 2500 дел в год ([история архива](https://archaeolog.ru/pub/archive/nauchno-otraslevoy-arkhiv-ia-ran-na-sovremennom-etape-istoriya-dostizheniya-i-perspektivy)). Полевые отчёты хранятся под шифром Ф-1. Р-1 ([каталог архива, т. 4](https://archaeolog.ru/media/series/arhiv/Archive_4_1965_68.pdf)).

В открытом доступе выложена только ранняя часть фонда: [электронные полевые отчёты](https://archaeolog.ru/pub/elektronnye-polevye-otchety) — сканы отчётов с текстом, чертежами, планами и фотографиями. Список строится из каталога [index.xml](https://archaeolog.ru/media/reports/index.xml), его копия — `reports_catalog.csv`.

Генеральная совокупность проекта — все отчёты электронного каталога на 11 октября 2026 года:

Это не выборка из всего архива, а его самая ранняя часть. Выводы проекта относятся к отчётам 1944–1949 годов и не переносятся автоматически на более поздние отчёты.

## Что делает конвейер

Для каждого PDF-отчёта:

1. **Рендер страниц** — PDF → PNG, 300 dpi (Poppler).
2. **Предобработка** — оттенки серого, медианный фильтр, выравнивание наклона (поиск угла по дисперсии горизонтальной проекции). Бинаризация отключена: она ухудшает OCR.
3. **Типизация страницы** — по плотности «чернил» страница относится к одному из типов: `dense_text`, `figure_or_table`, `mixed`, `image_or_blank`.
4. **OCR** — Tesseract, русский язык, модель tessdata_best.
5. **Извлечение сущностей** — регулярные выражения: персоны (ФИО), годы, топонимы, археологические термины, периоды.
6. **Отчёт по документу** — CSV, JSON и `report.md` в папке `<результаты>/<документ>/`.

Затем `analyze_results.py` собирает результаты всех документов и классифицирует документы по профилю макета (`textual`, `mixed_layout`, `visual_low_text`, `hybrid_other`), а `evaluate_ocr_quality.py` оценивает качество распознавания.

Все настройки — разрешение, бинаризация, модель, пути к программам — в `config.py`.

## Результаты исходной версии

Исходная версия конвейера (200 dpi, бинаризация Оцу, облегчённая модель Tesseract) обработала 44 отчёта, 2031 страницу. Это первые номера каталога, см. «Выборки внутри корпуса».

### Типы страниц

| Тип страницы | Страниц | Доля |
|---|---|---|
| `dense_text` | 889 | 43,8 % |
| `figure_or_table` | 792 | 39,0 % |
| `mixed` | 274 | 13,5 % |
| `image_or_blank` | 76 | 3,7 % |

По автоматической типизации исходного прогона больше половины страниц отнесены к типам, отличным от `dense_text`. Однако последующая ручная проверка обнаружила грубые ошибки классификатора: фотоальбомы могут попадать в `dense_text`, а машинопись — в категории рисунков. Эти доли не являются проверенным распределением макетов корпуса; фильтрация метрик по `page_type` ненадёжна.

### Качество OCR

Эталонной расшифровки нет, поэтому качество оценено косвенно: какая доля распознанных слов есть в словаре русского языка (pymorphy3). Подробно: [docs/ocr_quality.md](docs/ocr_quality.md).

| Качество страницы | Критерий | Страниц | Доля |
|---|---|---|---|
| хорошее | ≥ 85 % словарных слов | 58 | 2,9 % |
| среднее | 70–85 % | 152 | 7,5 % |
| плохое | < 70 % | 1139 | 56,1 % |
| пусто | < 20 слов | 682 | 33,6 % |

Доля словарных слов по корпусу — 47,7 %, медиана по документам — 42 %. Лучше 70 % распознаны только 6 из 44 отчётов.

## Эксперимент с настройками OCR

50 случайных страниц с плотным текстом (не больше 3 из одного отчёта) распознаны в 9 вариантах. Варианты сравниваются попарно на одних и тех же страницах, значимость проверена бутстрепом (95 % интервалы). Скрипт и полные результаты, включая таблицы значимости для всех пар вариантов: [experiments/ocr_tuning](experiments/ocr_tuning/summary.md).

| Изменение | Словарных слов | Словарных слов (количество) | Вывод |
|---|---|---|---|
| Исходный вариант: 200 dpi, Оцу | 48,0 % | 3376 | — |
| Без бинаризации | 63,7 % | +34 % | Главный эффект, значим (+13–18 п.) |
| + 300 dpi | 64,1 % | +38 % | Пустых страниц меньше (11 против 15); по доле словарных слов разница незначима |
| + модель tessdata_best | 63,9 % | **+44 %** | Словарных слов (количество) значимо больше (+2–8 %), распознавание на 30 % медленнее |
| psm 4 или psm 6 вместо psm 3 | 63,3 % / 62,8 % | ≈ | Незначимо |
| Адаптивная бинаризация Саувола | 48,3 % | ≈ исходному | Не помогает |
| Стандартная модель tessdata | 53,5 % | +16 % | Хуже облегчённой и tessdata_best |

По наблюдениям эксперимента бинаризация Оцу стирает тонкие штрихи бледной машинописи этой выборки; Tesseract лучше работает с оттенками серого. Без бинаризации распознавание улучшилось на 36 страницах из 50 и ухудшилось на 9.

Конвейер переведён на лучшую конфигурацию: без бинаризации, 300 dpi, tessdata_best. На двух самых трудных отчётах число слов, найденных в словаре, выросло с 418 до 787, а типизация страниц не изменилась.

Лучшая из протестированных конфигураций даёт около 64 % словарных слов на экспериментальной выборке. Это не точность OCR по эталону и не установленный потолок Tesseract.

### Исходное разрешение и рендер

По наблюдениям при подготовке эталонной выборки, сканы в PDF преимущественно имеют исходное разрешение 150 ppi, изредка 300 ppi. Рендер 300 dpi увеличивает изображение скана 150 ppi, но не добавляет исходной детализации. Поэтому эксперимент «200 против 300 dpi» сравнивал параметры рендера и масштабирование, а не обязательно разные разрешения исходного сканирования. Наблюдение не следует считать измерением всех 22 187 страниц.

### Выявленные ограничения извлечения сущностей

- `PERSON`: «Марра Академии Наук» (67), «Постановление Совета Министров» (29), «Научного Архива Института» (16), «Государственный Исторический Музей» (6). Учреждения и заголовки ошибочно классифицированы как люди; границы имени также могут быть неверными.
- `LOCATION`: встречаются фрагменты предложений, например «р. Камы и вытянута с востока на запад». Есть варианты «р. Кубани» и «р. Кубвни»; объединение требует контекстной проверки.

Девять отчётов имеют `entities = 0`: № 56, 133, 198, 229, 231а, 295, 306, 333 и 385. Это список для проверки, а не доказательство ошибки OCR: возможны нетекстовые страницы или отсутствие совпадений с правилами извлечения.

Причины ложных извлечений нужно проверить по `linguistics.py` и контекстам. Частотный CSV содержит только `type`, `text`, `count` и не позволяет сам по себе восстановить документ и страницу каждого совпадения. Исходные результаты v2 следует сохранять отдельно от исправленных производных.

## Эталонная выборка OCR (отложенное направление)

По отчёту предыдущего этапа подготовлены `ground_truth/sample.csv`, 30 исходных сканов в `ground_truth/images/` (около 53 МБ, без пересжатия) и `ground_truth/make_sample.py`. Состав: 21 страница машинописи, 3 рукописные страницы, 4 страницы с подписями к иллюстрациям, 1 таблица и 1 список.

В `sample.csv` записаны отчёт, страница, годовой слой, тип страницы, причина выбора и размер скана. Отчёты № 198, 54, 130а и 164 без текстовых страниц заменены резервными того же года. Воспроизводимость заявлена при `seed 2026`; извлечение сканов предусмотрено через `--extract`. Упомянутый в прежнем отчёте список из 42 отчётов требует сверки со скриптом: его связь с итоговыми 30 страницами пока не уточнена.

Эти файлы не проверялись повторно при анализе трёх итоговых CSV. Для `sample.csv` добавлено исключение `!ground_truth/*.csv` в `.gitignore`; сканы исключены правилами для PNG/JPG.

Полная расшифровка не входит в ближайшую дорожную карту. Проверка агентных задач ограничивается выбранными полями и свидетельствами.

### Протокол расшифровки: предложен, ещё не утверждён

- Сохранять опечатки оригинала, `ё`, латиницу, разбиение на строки и дефисы переносов.
- Нормализовать кавычки, тире и пробелы только при вычислении метрик.
- Обозначать нечитаемое как `[нрзб]`; способ исключения соответствующих участков из метрик ещё нужно определить.
- Включать колонтитулы, номера страниц и подписи «Рис. N»; исключать архивные штампы.
- Таблицы записывать построчно, разделяя ячейки символом `|`.

Открытые решения: теги `<рук>…</рук>` для рукописной правки, исключение водяного знака, теги `<зач>…</зач>` для зачёркнутого текста и способ подготовки черновика. Эталонная расшифровка не завершена; CER/WER полного прогона не вычислены.

### Пилотная версия и датасет планов

Первая версия конвейера, отработанная на 12 отчётах (404 страницы): отдельные скрипты для каждого шага.

`pdf_to_pages.py` → `preprocess_pages.py` → `analyze_pages.py` → `run_ocr.py` → `aggregate_ocr.py` → `analyze_corpus.py` → `extract_entities.py` → `summarize_entities.py` → `show_visualizations.py`

На её основе `build_plans_dataset.py` и `enrich_plans_dataset.py` собирают датасет страниц с планами, схемами и разрезами для будущей CV/ML-классификации. `dar-site/` — статическая страница со сводной статистикой по пилотному корпусу.

## Установка

Нужны Python 3.10+ и три внешних компонента:

- **Tesseract OCR** с русским языком — [установщик для Windows](https://github.com/UB-Mannheim/tesseract/wiki);
- **Poppler** — [сборка для Windows](https://github.com/oschwald/poppler-windows/releases), распакуйте в `tools/`;
- **модель tessdata_best** — [rus.traineddata](https://github.com/tesseract-ocr/tessdata_best/raw/main/rus.traineddata), положите в `tools/tessdata_best/`. Без неё используется модель, установленная с Tesseract.

```
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements_minimal.txt
```

Если программы лежат в другом месте, пути задаются в `config.py` или через переменные окружения:

```
set POPPLER_PATH=C:\path\to\poppler\Library\bin
set TESSERACT_EXE=C:\Program Files\Tesseract-OCR\tesseract.exe
set TESSDATA_DIR=C:\path\to\tessdata_best
```

## Запуск

```
python download_from_list.py
python run_pipeline.py --input input_reports --output results_v2 --skip-existing
python analyze_results.py
python evaluate_ocr_quality.py --results results_v2
```

Полный прогон v2 уже завершён; повторный запуск всего корпуса для получения этих сводок не требуется. Перед запуском `analyze_results.py` проверьте, что его настройки указывают на `results_v2`: CLI-параметры этого скрипта здесь не подтверждены.

`--skip-existing` пропускает уже обработанные отчёты, поэтому обработку можно прерывать и продолжать.

`--workers N` задаёт, сколько отчётов обрабатывается параллельно (по умолчанию 4, см. `WORKERS` в `config.py`). PDF рендерится порциями по несколько страниц, поэтому память не зависит от размера отчёта. По умолчанию на диск сохраняются только обработанные страницы и тексты OCR — около 2,7 МБ на страницу при 300 dpi; исходный рендер и отладочные картинки включаются настройками `SAVE_RAW_PAGES` и `SAVE_LAYOUT_DEBUG`.

Повторить эксперимент с настройками OCR:

```
python experiments/ocr_tuning/run_experiment.py
```

## Данные и права

Исходные отчёты и производные от них материалы (изображения страниц, OCR-тексты) в репозиторий не входят. Они принадлежат Институту археологии РАН и доступны в его [открытом архиве](https://archaeolog.ru/pub/elektronnye-polevye-otchety). Репозиторий содержит только код, список ссылок и сводную статистику.

## Ограничения

Корпус ограничен ранними отчётами и историческими практиками документирования. Точность OCR, сущностей и типизации не установлена по полноценному эталону. Авторское заключение не тождественно исторической истине. Причину неопределённости не всегда можно устранить просмотром скана или помощью человека. Пилот не доказывает универсальную надёжность агентов; для общих выводов необходимы расширение эксперимента, проверка переноса и отдельное исследование взаимодействия человека с Workbench.
